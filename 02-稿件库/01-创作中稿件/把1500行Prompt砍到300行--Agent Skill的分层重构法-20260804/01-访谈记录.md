## 访谈核心观点提炼

### 一、核心观点（5个）

1. **大代码文件到点必须分层重构（代码引子）**【来自 Q1、Q2】
   几千行挤在一份文件里，手动排查麻烦、AI 每次要吞整份文件 prompt 捉襟见肘、不符资深程序员代码规范。这不是"代码写错了"，是"文件太大、结构太乱"。代码到点该重构，Prompt 也一样。

2. **分层不是手设计，是让 AI 评估出开发提示词后 AI 去切（用 AI 治 AI）**【来自 Q3、Q4】
   作者把两份几千行 py 喂给 AI，AI 产出十分详细的拆分方案（P2-01~07 批次），作者直接用、不二次评估，AI 切层执行。但四次重构均失败。关键衔接：代码要分层，得先给 AI 一份"开发提示词"；而这份提示词自己也会膨胀（呼应①的恶性循环）。

3. **主线：Prompt/Skill 也得分层重构，但当时没思路无从下手**【来自 Q5】
   作者有几份反复用的 PRD/DEV 提示词（做客户项目用），越堆越长，当时没有重构思路，不知道怎么拆、拆了怕丢规则。这是本篇要解决的核心痛点。

4. **分层重构法（源文 5 个解法，作者委托"按文章编写"）**【干货主线】
   - 解法1 分层架构——位置即优先级：4 层（①全局不可违反规则最前 20-50 行；②核心方法论；③执行流程中间允许适度遗漏；④输出模板末尾利用近因效应），全局禁令只在第 1 层写一次后续只引用。
   - 解法6 外置知识——给 Skill 减负：规则类（行为约束）留 Skill，参考类（表结构/SQL 模板/报告格式）外置为引用文件，Skill 保持 300-500 行甜区。
   - 解法7 参考文件一致性——别让课本和规则打架：外置后易出现模板 SELECT 了被禁字段、示例只覆盖部分维度；修复原则：彻底删除被禁内容（注释也不行，注释也是 token）、示例必须完整覆盖、关键格式差异放显眼对照表。
   - 解法5 指令三明治——首尾呼应：对最关键 2-3 条规则在首尾各放一遍（首因+近因效应），区别于无序中间堆砌。
   - 解法4 结构化格式——降低理解成本：表格/编号列表/明确标题层级比大段自然语言更易被模型扫描。

5. **认知升华：Prompt 维护=代码维护（技术债），且有边界（反共识）**【来自 Q6】
   每次加规则=每次打 hotfix 补丁堆债，到点该重构。但不是所有 Prompt 都该分层：一两百行一次性短 Prompt 别折腾，长期维护几百上千行驱动 Agent 反复跑的才值得；分层也不是越细越好，过度工程自己绕晕。分层目的不是细，是让最重要规则待在该待的位置。
