一、任务目标

------

本项目希望收集真实生产环境中的<u><strong>非代码类超长程任务</strong></u>，用于评估 Claude Code、Codex 等智能体在复杂、长期任务中的规划、工具调用、执行、自检和迭代能力。

**合格题目要求：（两点同时满足）**

1. Claude opus SOTA和 GPT SOTA的分数按照考点打分低于60%

> 举例：某题有20个考点，每个考点按照0/1打分；模型命中8个考点，则模型的得分为：40%=8/20

2. Claude opus SOTA进行 250 轮以上的交互或GPT SOTA 200轮以上的交互，不能通过少量步骤直接完成

_*本任务会查重，如发现题目与其他任务（无论是进行中的任务还是已结束的任务）中的题目相似度高题目按作废处理，是否相似以项目组判断为准。__

**任务可采用以下两种形式：**

1. 单轮任务

2. 多轮任务
   
   1. 静态多轮任务
   
   2. 动态多轮任务（鼓励优先采用）

三、解释说明
------

1. ### **非代码类**任务

判断方式：关注用户真正要解决的问题，而不是智能体过程中有没有写代码。如果现实中的从业者通常不需要编程，或只在少数环节使用编程，这个任务就属于非代码类。例如，整理资料、分析数据、制作表格、撰写报告等任务中，智能体可能会调用命令行工具或编写脚本来提高效率，但这不会把任务变成代码类。只有当任务的主要目标是开发软件、修改代码或排查程序问题时，才属于代码类任务。

_*任务是否属于代码类以项目组判定为准，不确定的专家可先发prompt验证_

2. ### 任务类型

3. #### 单轮任务

用户一次性给出目标，Agent持续执行，直到满足最终验收条件。典型形式为 `/goal` 模式。

这里的“单轮”是指用户只需提交一次任务要求。用户只定义最终目标、约束条件和可验证的验收标准。智能体自行完成：任务拆解；执行顺序安排；工具调用；中间成果检查；错误修复；方案迭代；最终验收。

用户不需要反复输入“继续”。智能体应持续推进，直到所有达标条件均已满足，或者确认存在无法自行解决的真实阻塞。出题时，不应把详细操作步骤全部写死。重点应放在最终状态、硬性约束、输入材料和验收条件上，使智能体拥有自主规划空间。

2. #### 多轮任务

设计时需要说明每一轮为什么必要：后一轮应基于前一轮的产物、反馈或新发现继续推进，而不是提出一个可以独立完成的新任务。整体上，多轮之间要有清晰的递进关系和强关联性，用户每次追加的信息或要求都应改变智能体下一步的判断、方案或产物。

##### 2.1 静态多轮（5轮以上）

静态多轮是指预先固定每一轮发送给 assistant 的 prompt。无论 assistant 在上一轮产出了什么内容，后续用户提示词基本保持不变。设计静态多轮时，仍需保证各轮存在前后依赖。不能把一个单轮任务机械拆成多条提示词，也不能把多个独立任务按轮次排列。

静态多轮适用于：

* 任务流程和用户反馈可以提前确定；

* 需要保证不同被测智能体收到完全相同的输入；

* 评测重点是固定流程下的执行稳定性；

* 后续要求不依赖智能体产物中的具体问题。

##### 2.2 User simulator 动态多轮任务（5轮以上）

动态多轮是指由另一个 agent 扮演 user simulator，根据 答题agent 当前提交的产物进行审阅，再决定下一轮提出什么反馈、补充什么信息或增加什么要求。动态多轮更接近真实用户与智能体合作的过程，因此在条件允许时应优先采用。多轮互动应来源于任务本身的不确定性和决策需要，不能为了增加轮数故意隐藏本应在开题时提供的关键信息，也不能机械地重复要求智能体继续。

模拟用户可以在合理时机：

* 回答智能体必须确认的问题；

* 提供尚未给出的业务信息；

* 对阶段性成果提出意见；

* 在多个方案之间作出选择；

* 根据新发现调整部分要求；

* 指出不符合真实需求的地方；

* 验收或驳回智能体的交付物。

出题要点：

* 需要通过 user_sp 给其输出内容一些约束，保证每次输出内容相对稳定一致；

* 需要让user agent输出的语气和内容尽量贴近真人（避免输出长篇大论）。

* 建议输出给 答题agent 的消息字数<500字

* 避免user agent把ground truth/rubrics等泄露给 答题agent；避免user agent过度干预、直接替assistant把活干了，应该只指出问题点，不要说具体怎么改。

* user agent可以设置多个角色，但是目前由一个agent扮演。所以各角色之间的信息无法完全隔离。

* 需要设置合适的终止条件，或者交互轮次上限

3. ### 任务的真实性与整体性

#### **真实性**

题目应来自或高度接近个人、学校、企业、科研机构等真实环境中的复杂工作。应避免纯架空、只为增加操作轮次而设计的小游戏式任务。游戏相关题目只有在其对应真实游戏开发、测试、运营或内容生产工作时才合格。判断标准是：现实中是否确实存在某类人员需要完成这项工作，以及题目中的成果是否具有实际使用价值。

**多轮/长程任务的 Hack 式表述的说明：**

题目应以真实业务场景和真实需求为出发点，用业务委托方通常会采用的口吻交代任务。Prompt可以明确目标、输入材料、交付物、质量标准和必要的业务约束，但不应为了贴合出题要求，人为规定模型的作答过程。

模型在完成任务时采用多少步骤、是否并行、何时检查、需要几轮修正以及运行多久，应主要由任务本身的复杂度和实际执行结果自然决定。不要在Prompt中刻意增加现实委托方通常不会提出的流程要求，包括但不限于：

* 强制任务必须运行若干小时；

* 强制拆成指定数量的阶段或分支；

* 强制设置若干验收关口、失败次数或修正闭环；

* 无实际业务必要，却要求模型必须增派、暂停或终止子任务；

* 为体现状态维护，机械要求持续记录大量中间状态；

* 直接使用“长程任务、工具链、Trace、轮数、复杂度、验收关口”等明显来自出题说明的措辞。

> 例如，“请完成数据清洗并提交可复现的分析结果，发现异常后应修正并重新验证”是合理的业务要求；而“本任务必须包含三个验收关口、至少两次失败重跑，并运行四小时以上”则属于明显为了满足出题指标而设计的Hack表述。

判断原则是：如果去掉某项流程要求，不影响真实业务目标、风险控制或交付质量，但会降低题目在出题指标上的复杂度得分，那么该要求很可能属于Hack。

合理的安全、合规、审计和复现要求可以保留，但需要能够体现其真实业务必要性。

#### **整体性：**

不能把多个彼此独立的小任务简单拼接成一个“大任务”。题目中的不同板块、阶段和交付物之间，应当存在较强的依赖关系。例如：

* 前期调研结果决定后续分析框架；

* 数据分析结论影响方案选择；

* 方案选择进一步影响预算、排期和材料内容；

* 后期审查发现的问题会迫使智能体返回前序阶段修改；

* 某个关键假设发生变化时，多个下游成果都需要同步更新。

一个简单的判断方法是：

> 如果可以将题目自然地拆成两个互不影响、可以分别交付的任务，那么它通常不符合要求。

优秀任务应具有“牵一发而动全身”的特征：前后环节相互制约，局部修改会影响整体结果。

4. ### 考点

5. #### 目的
* 自测的置信度更高，考点的设置是为了稳定模型的评分，尽量避免一些模型评分的幻觉

* 题目越来越难的背景下，gt的得到越来越难，考点中体现要求就越发重要，更需要专家自己来提供更好的考点
2. #### 考点的本质
* 考点需**客观具体地呈现题目的关键点、难点，作为合理且置信的判分标准去判卷**，是题目对模型能力的考察点

* 本质上考点应**从prompt出发**，由题目得来，而不是直接照搬标答，应避免出现与标答严重过拟合的不合理外推问题

* 考点需合理把握颗粒度，以各位专家的专业视角以及对题目的把握，选择考点撰写什么时候需要精准什么时候需要适当给范围；对合理的开放问题撰写考点时，考点的尺度是关键，需要客观、有评测价值且不超出题目要求

* 考点要实现必须能够由机器和人工区分模型产物的好坏，并且不同能力水平的模型应表现出明显差异，即使是当前SOTA模型，也应仍有较大的提升空间

* 考点的设置是为了**稳定模型的评分**，所以考点应全面覆盖题目的要求，突出题目的关键考察点，出题人必须提交完整的考点：如需要检查哪些交付物；每个考点的判断标准；如何处理开放性内容；如何检查多个文件或环节之间的一致性；如何判断最终成果是否具备实际可用性等，具体视题目而定
3. #### 一条合格的考点的基本要求

|               |                                                                                                                                                                                           |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **rubrics要求** | **具体释义**                                                                                                                                                                                  |
| **完整性**       | * 完整的rubrics需要涵盖Prompt中的所有需求，不漏掉任何一个检查点<br>  <br>* 撰写rubrics应从题目出发，需为必答点、重要的判分点，与题目作答关系不大或者题目未要求的不用涉及                                                                                     |
| **独立性**       | * 每一条rubric都应是"原子化的"，即一条rubric只检查一件事（要么0分，要么1分）<br>  <br>* 同时也要避免本质重复的rubric                                                                                                              |
| **描述清晰**      | * 合格的rubric表述方式应该为正向的陈述句，不能带有“是否xxx”的字眼<br>  <br>* 考点必须客观、可判定，避免主观描述和模糊抽象的表达（eg：文风简洁有力、游戏打击感强等，这类无法判分）<br>  <br>* 考点应可以根据模型回复判断其是否为 TRUE（正确）或 FALSE（错误），避免使用主观或模棱两可的考点，否则可能会对某一陈述是否成立产生分歧 |
| **判分精准**      | * 对于收敛的考点，需要在rubric中明确写出精确的验证结果<br>  <br>* 对于半收敛的问题，需要在rubric中构建清晰明确的判分标准，给相对开放的答案一个合理的得分规则<br>  <br>* 若有需批量验证的考点，可以合理地设置典型抽检点                                                            |
| **真实准确**      | * 考点中包含的答案必须真实且准确，需要进行必要的研究来核实答案的正确性<br>  <br>* 考点涉及到数据，需要明确单位、保留小数位数和允许的误差范围<br>  <br>* 涉及计算逻辑的考点，应说明计算口径、输入字段、输出字段和结果位置；需要保留公式时，应明确要求不能仅填写静态值                                           |

三、提升任务复杂度的tip
-------------

<u><strong>提升难度是任务本身够难而不是故意刁难模型</strong></u>，是真实工作场景中人会遇到的困难而不是人为设置的卡点；<u><strong>在出题时把模型当成自己的同事或实习生</strong></u>。在工作或科研场景中，人类在完成任务的时候往往不知道完成这件事的正确路径，很多时候需要自己摸索方法或者需要从团队的只言片语（群聊，规章制度，过往任务沉淀的约定俗成的规矩）整合信息。

### prompt部分

1. 从自身工作出发，优秀的题目往往非常贴合真实的工作环境。

2. 合理不在prompt中提供部分信息，合理在部分关键信息做模糊处理：比如模型需要通过自己的推理甚至自己的判断才能找到完成任务的关键数据。比如一些专家会详细介绍每一份附件的内容，详细写出计算的公式和考点。可以适当进行留白让模型自行检索或自行寻找信息。

3. 目前模型做的好的部分：按照固定的流程完成即可完成，当题目有清晰的完成路径或者推理路径时，模型完成度比较高；所以专家在出题可以适当模糊完成路径，不用描述的非常清晰，可以改为给模型留下可推理的线索，或者鼓励模型自己作出决策。

4. 尝试尽可能扩大项目范围/覆盖完整项目周期：
   
   1. 优先选择原本就需要多人或多团队密切协作的大型项目，并把相关合作方或上下游工作纳入同一任务。

> 例如，一个产品发布项目可以同时涉及用户研究、竞争分析、定位设计、预算规划、发布材料和风险审查。但这些工作必须围绕同一个产品和同一组关键决策展开，不能只是若干独立任务的集合。

3. 不要只截取项目中的单一环节，应尽量覆盖从发现问题到最终交付、验证和修订的全过程。

> 例如：
> 
> * 投资项目：前期访谈与行业研究 → 商业分析 → 财务尽调 → 法务尽调 → 风险判断 → 投资材料撰写 → 多轮审查与修订。
> 
> * 经营改进项目：发现问题 → 收集数据 → 提出假设 → 设计分析或实验 → 验证假设 → 制订改进方案 → 深化方案 → 形成落地计划。
> 
> * 科研项目：文献梳理 → 研究问题定义 → 方法设计 → 数据处理 → 结果分析 → 稳健性检查 → 论文材料撰写 → 审稿意见回应。
> 
> 各阶段必须共享信息并相互影响，不能只是按顺序排列的独立流程。

### 附件部分

1. **提升数据的获取难度**：真实的工作中往往有很多脏数据，真正有用的信息往往藏在噪声下；目前很多专家提供的数据太干净，真实工作环境中的原始数据的数据格式、数据质量、数据内容往往并不标准甚至充满错误。

2. **增加合理矛盾**，在关键数据/刚需信息部分制造矛盾点：不同数据源的数据需要模型自行找到证据判断权威性；任务具有时间跨度的时候，不同时间点的数据模型需要根据当前时间找到正确的数据（比如国家统计局数据修订，法律条款的更新）；不同口径的计算结果不同，模型需要找到正确的计算口径

3. 设置需要模型需要从不同的附件中整合信息的题目，优秀的题目中的关键信息往往分散隐藏在不同的附件中，模型只有真的读懂了附件中的内容，把零散的信息拼凑出来才能完成任务。在现实生活中往往也是这样，完成领导任务所需要的信息不会只存在在一个文件中，往往需要人从不同的文件中拼凑零散的信息才能得到完整的信息

4. 目前模型做的不好的部分：需要自己做决策；给模型各方的意见需要模型

### 标答部分

标答鼓励适当的开放性，不必保证只有一个正确答案。真实世界中的复杂工作往往允许多种合理方案，核心是最终结果是否符合目标、证据是否充分、决策是否合理以及成果是否可用。

### 提升轮次

1. 增加模型需要交付的产物的数量和种类

2. 联网搜索信息

3. 涉及不同规则的大量数据的清洗和处理

4. 让模型自己进行选择和判断
   
   

### 其他提升难度相关的tips

> 希望专家读到以下思路时，去回忆真实的场景出题。而不是按我们的方式从零去虚构一个题目。

1. #### **多证据冲突，而且"哪个证据有效"不能靠简单的最新日期判断**

这是我认为比较有效的一类。

例如同时给：

* 正式制度 v3；

* 一个日期更晚但尚未生效的 v4；

* 一封管理人员邮件，对某一条规则做临时豁免；

* 后续又有一封邮件撤销豁免；

* Excel Summary 是最新生成的，但底层用的是旧快照；

* 一个签字文件时间较早，却具有最高权限；

* 前台界面显示 Complete，但底层依据的文件是草稿级别；

* 一条记录后续被撤销。

模型不能做“全文搜索 → 找到一句话 → 使用”。

它必须自己建立：

**证据 → 权限 → 生效时间 → 适用对象 → 当前状态**

这样的状态模型。

这里尤其有效的一种设计叫**显著性反转**：

> 最醒目、最像答案的材料，是错误的。
> 
> 真答案需要综合几个不那么显眼的证据才能得到。

* * *

2. #### **总任务很明确，但真正关键的“判断标准”需要模型自己推出来**

Prompt 可以非常清楚地告诉模型最终要做什么，难点不需要靠故意把题目写模糊。

真正有难度的是：

> 用户告诉了模型“要选谁、要判断什么、要做什么决策”，但没有直接告诉模型“这次决策真正应该重点看什么”。

例如任务要求从几个供应商中选一家。

材料里可能大量介绍：

* 产品质量；

* 报价；

* 公司规模；

* 获奖情况；

* 综合评分；

* 甚至已经做了一张很完整的供应商能力排行榜。

但结合项目当前情况后，真正决定成败的可能是：

**谁能够稳定按期交付。**

而“交付能力”本身又没有直接做成一个评分字段，只能从历史延期次数、订单积压、产能利用率、临时停产记录等材料里自己推出来。

模型很容易沿着材料已经搭好的评价框架继续分析，最后选出一个“综合能力最强”的对象。

问题在于：

> 它回答得很完整，但解决的不是当前最关键的问题。

这类题考察的是模型能否从总体任务进一步恢复出：

**当前瓶颈 → 真正判断标准 → 应该读取哪些证据 → 最终决策**

而不是材料给什么指标，模型就分析什么指标。

* * *

3. #### **同一批对象同时命中多个规则，而且规则之间没有固定的优先级**

简单的规则题通常是：

**A 优先于 B，B 优先于 C。**

这种模型很容易处理。

更难的是，规则优先级会随着“同时命中了哪些条件”发生变化。

例如：

* 同时符合 A、B 时，先处理 A，再处理 B；

* 同时符合 B、C 时，B 覆盖 C；

* 同时符合 A、C 时，反而 C 优先；

* 同时符合 A、B、C 时，不再沿用前面的规则，而触发一个特殊组合规则；

* 某些对象还有单独的例外；

* 例外又只在特定时间或状态下生效。

这时候规则关系已经不是简单的：

**A > B > C**

而是：

**对象当前状态 → 命中规则组合 → 确定处理顺序 → 判断覆盖关系 → 再检查例外**

真正容易出错的地方是：

> 模型可能把每条规则都理解对了，但组合到一个具体对象上以后，处理结果仍然是错的。

这类设计很适合审批、税务、优惠资格、保险理赔、价格政策、库存处理、风险分类等任务。

* * *

4. #### **正确答案可以是“没有答案”“不能继续”或者“当前条件下无解”**

模型有一个很明显的倾向：

> 用户让我解决一个问题，我就应该给出一个结果。

如果问题非常简单，模型通常能识别矛盾。

例如直接问：

> 有没有一个数字同时大于10又小于5？

模型当然知道没有。

但如果同样的矛盾被埋进一个复杂任务的中间环节，模型就更容易忽略。

例如在一个真实的采购任务里同时存在：

* 预算上限；

* 最低技术标准；

* 最晚交付日期；

* 最低采购量；

* 供应商资格要求；

* 地域限制。

每一个条件单独看都很正常。

模型可能认真做完价格比较、供应商评分、风险分析，最后推荐一个“最优方案”。

但真正需要检查的是：

> 有没有任何一个方案能够同时满足所有硬约束？

答案可能是：**一个都没有。**

类似的情况还包括：

* 当前证据不足以确定唯一结论；

* 两个必要条件互相冲突；

* 缺少一个不可替代的输入；

* 所有候选对象至少违反一条硬规则；

* 当前流程根本没有达到进入下一阶段的条件。

这种题最有效的地方在于：

> 让模型完全可以继续算，而且还能算出一个看上去非常漂亮、非常合理的结果。

真正的难点是它能不能意识到：

**这一步原则上就不应该继续往下算。**

* * *

> 使用以上tips的时候注意不要把“假陷阱”变成“真漏洞”感来源

--------

出题人可以优先回顾以下经历：

1. 自己曾在个人、团队或组织中完成过的复杂大型项目；

2. 在校期间参与过的重要科研项目、毕业论文或长期课题；

3. 曾经需要多人、多部门或上下游团队协同完成的工作；

4. 自己使用 Codex、Claude Code、OpenClaw 等工具时，经过十余次人工交互并投入大量时间才完成的项目；

5. 一旦某项数据、假设或决策改变，就需要同步修改大量下游成果的项目；

6. 因质量要求高、资料复杂或反馈频繁，必须经历多轮审查和返工的项目。

优先把真实经历改造成题目，而不是先设想一个抽象任务，再人为添加步骤使其变复杂。

五、常见不合格情况
---------

以下题目通常不符合要求：

* 核心目标是开发、调试或维护软件；

* 只需少量操作即可完成；

* 通过复制粘贴或机械重复来凑足轮次；

* 将多个无关任务打包在一起；

* 不同阶段互不影响，可以独立完成；

* 纯架空的小游戏或虚构操作；

* 没有明确的最终交付物；

* 无法判断产物好坏；

* 评分标准只依赖主观印象；

* 开放题没有 pairwise 或其他可靠评估方案；

* 所谓多轮只是用户不断输入“继续”；

* 关键信息被不合理隐藏，只为迫使智能体追问；

* 当前领先智能体的初稿稍作修改即可直接使用；

* 任务复杂度主要来自格式要求，而不是实际问题本身。

六、结算说明
------

* 每人允许出3道单轮题，3道静态多轮题，3道动态多轮题，鼓励出海外题，同一专家出的题目需要有明显差异，不能雷同或者相似度过高。

> 海外题说明：需具备真实的海外业务语境。题目中的研究标的、数据来源、文件材料、市场规则和交付场景均应来自海外市场，不能只是将中文题目或国内业务场景简单翻译成英文，如果题目背景本身不具有国内和海外的差异（例如单纯的数据分析题），无论是何种语言均不算做海外题，是否能算作海外题以项目组判定为准，不确定的专家可提前提交prompt验证。
